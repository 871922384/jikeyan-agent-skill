# 截止日倒排

## 操作步骤
1. 向用户确认实际截止时间、时区、交付物、外部依赖、合作者可用性；用 `get_project` 看已有未完成节点与等待项。区分硬截止和建议完成日，不把口头估计写成确定事实。
2. 以截止为终点按 [判断标准](thresholds.md) 的最终检查与提交、外部反馈、合作者确认三行预留草案缓冲；与实际约定、工作日和任务依赖对齐。可并行的活动不要重复累加，期刊要求或用户偏好优先。
3. 列出每一项产出、前置依赖及决策点。若已有节点冲突，列出原日期、建议日期、影响和可选方案，请用户决定；不要静默覆盖或重复创建。时间不足时提出缩减范围、并行或申请延期，并说明取舍，不保证完成。
4. 经用户确认后，先 `get_schema` 核对节点种类，再用 `get_project` 找已有节点 ID。每项用 `upsert_node` 传 `project_id`、kind、title、`due_at`，按需传 detail、tz；更改现有节点带 `target_id`。每项先传 `dry_run` 为 true 检查回执，正式写入后重读；逐次考虑版本变化。截止种类必须有截止时间，日期按所选时区解释到当日结束。

## 示例：课题甲投稿倒排
假设期刊乙截止 2026-12-01 23:59（Asia/Shanghai），用户已确认 2026-11-10 可提供材料，且外部与合作者确认可以并行。

| 日期 | 工作与可验证产出 | 依赖 |
| --- | --- | --- |
| 2026-11-10 | 完成材料清单，发起外部反馈及作者确认的准备 | 用户提供材料 |
| 2026-11-14 | 交付外部反馈请求，约定 2026-11-28 前返回 | 请求材料完成 |
| 2026-11-21 | 合作者收到完整确认稿，约定 2026-11-28 前确认 | 初稿完成 |
| 2026-11-28 | 汇总反馈、确认稿件并开始最终检查 | 外部反馈和合作者确认 |
| 2026-12-01 | 完成系统提交并保存凭证 | 全部检查通过 |

假设现有节点“作者确认”为 2026-11-30：报告与新计划冲突及压缩检查缓冲的后果，先请用户选择改期或调整范围。选择改期后，以该节点 ID 预演更新而非新建；正式执行后重读核对。若外部反馈无法在约定时返回，需重排或请用户决定延期。

## 常见坑
日期不是已获得的承诺；不要在未知的期刊截止时刻使用当天结束代替真实时刻。节点标签不是成员指派；`dry_run` 不落库也不保证后续无冲突。
