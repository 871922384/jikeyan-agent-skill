# 写入规范

## 操作步骤
1. 不写患者姓名、住院号、诊断或随访原文；仅管理科研课题，不作医学结论或诊疗建议。不替用户指派、管理成员或发送催询；这些不在 MCP 内。事实来自 MCP，判断标明依据。
2. 用 `get_schema` 核对模板、枚举、允许字段及已公开长度限制，再读课题确认目标、版本、已有子项和用户意图。工具参数以 `mcp/src/jikeyan_mcp/tools.py` 为准，不将底层 HTTP 操作字段直接当作 MCP 参数。
3. 每次写入先传 `dry_run` 为 true：核对 `snapshot` 的课题、预期字段和假设执行后的 version；逐条看 `action_receipts` 的动作、目标及摘要，检查是否命中已有课题。预演不落库，预演生成的目标 ID 和版本不代表已经存在。确认符合意图后以相同业务内容正式写入，再读回。归档为破坏性操作，预演及执行前都须用户明确确认；当前 MCP 无撤销归档。
4. 正式写入超时先重读，确认是否已经成功，不能盲目重复创建节点、等待项或轮次；修改子项先找 ID 并传 `target_id`。课题可用稳定 `external_ref` 去重：同账号未归档课题命中返回已有课题；已归档不参与去重。

## 幂等、并发与权限
HTTP 的 `Idempotency-Key` 标识一次成功写请求，可原样重放；预演既不读取也不占用该记录。它不同于标识课题来源身份的 `external_ref`，后者仅对创建课题去重。当前 MCP 不提供 HTTP 幂等键参数，不得虚构；节点更新要用目标 ID 和重读来避免重复。

`base_version` 可显式传入；省略时 MCP 先读当前版本。遇到 version_conflict 时，读取错误的当前版本提示并用 `get_project` 重读所有相关事实，比较其他人变更与用户意图，必要时请用户选择；重新构造参数、预演，再正式写入。不能只换版本号强行覆盖；预演之后仍可能发生冲突。

403 表示权限限制而不是内容格式问题：只读 Key 不能写；限定范围 Key 不能写范围外课题，也不能新建。向用户说明具体限制及受影响操作，请其在 App 中决定是否重新生成合适权限的 Key；不绕过限制，不索取或打印密钥。读取错误的 code、detail、details、hint；按 hint 及允许值纠正一次再试，若无 hint 则看 details。权限或冲突原因未解决时不要反复重试。

## 示例：课题甲节点变更
用户同意把现有节点的截止改到 2026-11-20。先读课题取得节点 ID 和版本，用 `upsert_node` 携带 `project_id`、kind、title、`target_id`、`due_at`、`base_version` 和预演标记。回执显示目标为该节点、预期截止正确，才正式执行；如返回版本冲突，重读后发现对方已改为 2026-11-18，先请用户决定采用哪个日期，再预演。正式成功后复读核对。

## 常见坑
预演快照不是已保存结果；创建课题去重不让子项自动幂等；错误 hint 不是授权；不得把受到权限拒绝的预演报告为成功。
