# 判断标准：草案，待 Rex 确认

这些提示线与默认缓冲均为草案，待 Rex 确认；不是服务端结论或医学判断。用户明确偏好优先，可写在 `status_note` 或自己的 Agent 记忆中。阶段行仅适用于论文模板；其他模板以 `get_schema` 为准。

| 项 | 提示线 | 停滞 / 需跟进线 |
| --- | --- | --- |
| 课题整体无任何更新（节点、等待项、时间线） | 14 天 | 30 天 |
| 阶段 `idea` | 45 天 | 90 天 |
| 阶段 `drafting` | 60 天 | 120 天 |
| 阶段 `internal_review` | 14 天 | 30 天 |
| 阶段 `submitted`（等分配或初审） | 14 天 | 30 天 |
| 阶段 `under_review`（外审） | 60 天 | 90 天，可礼貌询问编辑部 |
| 阶段 `revision` | 距修回截止 ≤14 天 | 距修回截止 ≤7 天或已逾期 |
| 等待内部对象（合作者、科室、统计）无回复 | 7 天 | 14 天 |
| 等待期刊、编辑部或外部机构无回复 | 30 天 | 60 天 |
| 截止类节点临近 | ≤7 天 | ≤3 天或已逾期 |
| 默认缓冲：最终检查与提交 | 3 天 | 截止前预留；按实际系统及工作日调整 |
| 默认缓冲：外部反馈 | 14 天 | 以实际约定和截止压力调整 |
| 默认缓冲：合作者确认 | 7 天 | 以合作者可用性和约定调整 |

## 使用与局限
`stage_entered_at` 是当前阶段进入时间，`days_in_stage` 是 UTC 向下取整的整数；为 null 时无法计算。老课题按历史修订回填，可能比真实进入时间晚，只会低估停留时间，不会高估：超线可信，未超线不能证明没拖。上线后阶段真正变更时记录精确；无法区分来源时按可能近似处理。对阶段以外的事实分别对照各行，标注时点。

`get_project` 只给未完成节点与等待项和有限进展；`get_changes` 首次游标不回放历史。覆盖不足不能证明整体无更新；`days_since_update` 不等于最后回复时间，需用户确认。缓冲是预算而非保证，外部反馈和合作者确认可能并行，不能无依据叠加或压缩。

## 示例
2026-11-06 读取论文课题甲处于初审阶段，阶段时间为 2026-09-01，整天数为 66；对照初审行已超过需跟进线。若是历史回填，该值仍支持超线，但不代表知道确切进入日期。先让用户核实当前投稿情况，再考虑起草询问。

## 常见坑
不要拿课题更新日代替阶段进入日；不能因为 null 或回填值未超线就断言正常；不要把草案缓冲说成期刊要求。
